## 一、我踩过的坑（问题 → 根因 → 解决 → 面试考点）

> 每个坑的「面试延伸」是面试官可能的追问，提前想好怎么答。

### 坑 1：`pip install` 成功，但 `import` 报错

- **现象**：`pip install openai` 显示成功，`python -c "import openai"` 却报 `ModuleNotFoundError`。
- **根因**：机器上有两个 Python 解释器（Anaconda 的 3.13 和官方的 3.10），`pip` 命令指向 Anaconda，`python` 指向 3.10。包装进了 3.13 的 site-packages，运行时用的却是 3.10。
- **解决**：用 `python -m pip install`，让 `python` 对应的解释器去装，保证一致。
- **面试延伸**：
  - Q：怎么排查"装上了却 import 不到"？A：`python -c "import sys; print(sys.executable)"` 看运行时用的是哪个解释器，`pip show 包名` 看装到哪了，两者对不上就是环境错位。
  - Q：`python -m pip` 和 `pip` 区别？A：前者强制用当前 `python` 绑定的 pip，后者取决于 PATH 里先找到哪个 pip。

### 坑 2：脚本文件名和包名撞车

- **现象**：`cd eval && python eval.py` 报 `No module named 'eval.tasks'; 'eval' is not a package`。
- **根因**：脚本文件叫 `eval.py`，又有个包目录叫 `eval/`。运行脚本时，Python 把 `eval.py` 当成了模块而不是 `eval` 包，`from eval.tasks import ...` 就找不到包了。
- **解决**：导入改成 try/except 回退（优先 `from eval.tasks`，失败则同目录 `from tasks`），并统一用 `python -m eval.eval` 从项目根目录运行。
- **面试延伸**：
  - Q：`python -m eval.eval` 和 `python eval/eval.py` 有什么区别？A：`-m` 以模块方式运行，会把当前目录加入 `sys.path`，且 `eval` 被正确识别为包；后者 `sys.path[0]` 是脚本所在目录。
  - Q：相对导入 `from .tasks` 和绝对导入 `from eval.tasks` 区别？A：相对导入要求必须是包（配合 `-m` 或作为包被 import），绝对导入更依赖 `sys.path`。这个坑让我真正搞懂了 Python 的 import 机制。

### 坑 3：入口脚本缺路径处理

- **现象**：`python agent/agent.py` 报 `No module named 'config'`。
- **根因**：直接运行脚本时 `sys.path[0]` 是**脚本所在目录**（`agent/`），不是项目根目录，`config.py` 在根目录下找不到。
- **解决**：入口脚本顶部用 `sys.path.insert(0, os.path.dirname(os.path.dirname(os.path.abspath(__file__))))` 把项目根目录加进去。
- **面试延伸**：这是 Python 项目结构的基本功——入口脚本和库代码的边界要分清，入口负责把根目录放进 `sys.path`，库代码用干净的绝对导入。

### 坑 4：API key 复制时多了个前缀

- **现象**：`AuthenticationError: api key ... is invalid`。
- **根因**：占位符本身是 `sk-` 开头，复制真实 key 时保留了占位符的 `sk-`，变成 `sk-sk-...`。
- **解决**：去掉多余的 `sk-`；自查用 `print(config.API_KEY[:7])` 看开头是否 `sk-sk-`。
- **面试延伸**：Q：密钥应该怎么管理？A：别硬编码进代码、别提交到 git（用 `.gitignore` + 环境变量）；这个项目为了新手友好用配置文件 + 环境变量回退，生产会用 secrets 管理。

### 坑 5：真实数据是脏的，工具一碰就崩

- **现象**：数据里故意埋了两处脏数据——id=27 缺 `specs`、id=28 缺 `review_summary`。工具用 `p["review_summary"]` 直接下标访问会 `KeyError`，整个 agent 挂掉。
- **根因**：真实电商数据一定不规整——缺字段、价格是范围字符串、重复条目。理想数据才整齐。
- **解决**：工具层统一用 `.get(key, 默认值)` 防御性解析，缺字段返回「暂无」而不是崩溃。
- **面试延伸**：这是「生产经验」的味道——agent 的工具本质是接外部数据，外部数据不可信，工具层必须是健壮的边界。能说出"EAFP vs LBYL"（`try/except` vs `if key in dict`）会加分。

### 坑 6：评估任务之间互相污染（状态泄漏）

- **现象**：跑评估时，「偏好记忆」类任务调 `update_user_preferences` 把偏好写进了共享的 `memory.json`，结果**后续任务读到了这个残留偏好**，在回答里提到它，干扰了结果。
- **根因**：任务之间共享了同一个记忆文件，前一个任务的副作用泄漏到了后一个任务。
- **解决**（已修复）：用 `contextvars` 给记忆加"会话级"隔离——`run()` 接收独立的记忆文件路径，评估时每个任务用独立临时文件、用完清理。已验证：评估后全局 memory 文件保持不变，任务间零泄漏。
- **面试延伸**：这是「评估可信度」的核心——**评估本身必须无状态**。如果评估顺序不同结果就不同，那这个数字不可信。测试隔离（test isolation）是软件工程的基本功，agent 评估也不例外。

### 坑 7：硬规则检查把「预算重述」误判成「超支」

- **现象**：`check_budget` 用正则抓回答里所有「数字+元」，结果 agent 说"50 元以下没有，最便宜 399 元"这种**正确回答**，被误判为超预算。
- **根因**：正则没有语义，分不清「推荐价 / 预算重述 / 替代品价格 / 记忆里的数字」。
- **解决**（已修复）：双管齐下——`llm_judge` 增加「预算合规」字段（它懂"左右/以下/替代"的语义），`check_budget` 正则只保留"诚实拒绝不算超支"的减误报逻辑。结果：误报从 5 次降到 0 次。
- **面试延伸**：这个坑直接引出一个高级话题——**评估本身也要被评估（eval the eval）**。硬规则的优势是确定性强、可复现，劣势是语义盲；LLM-judge 反过来。所以要用「双通道」，用硬规则兜确定性错误，用 judge 兜语义。面试官问"你的评估可信吗"，这就是答案。

### 坑 8：模型反复调用同一个工具 / 死循环

- **现象**：日志里模型连续多次调 `search_products`，浪费 token，迟迟不给结论。
- **根因**：prompt 没明确"什么时候该停"，模型倾向于继续探索。
- **解决**：`MAX_STEPS` 设上限兜底 + prompt 明确"信息足够就停止调用、直接给结论"。
- **面试延伸**：Q：怎么防止 agent 烧钱？A：三层——`MAX_STEPS` 硬上限、低 `temperature` 减少无意义探索、prompt 明确终止条件。token 成本是生产 agent 的头号现实约束。

### 坑 9：MinGW 编译的 .pyd 一 import 就崩

- **现象**：`ImportError: DLL load failed while importing fast_index: 找不到指定的模块`。
- **根因**：MinGW 编译的扩展依赖 libstdc++/libgcc 运行时 DLL，Python 运行时找不到。
- **解决**（已修复）：编译时加 `-static-libgcc -static-libstdc++ -static` 静态链接，生成自包含的 .pyd。
- **面试延伸**：这是 C/C++ 部署的老问题——动态链接 vs 静态链接的 trade-off。能说清"为什么 MinGW 编译要静态链接 libgcc"，说明你真的自己编译过，不是抄教程。

### 坑 10：.pyd 放在子目录，`import` 找不到

- **现象**：`fast_index.pyd` 明明编译好了，`import fast_index` 却失败（`_HAS_CPP_INDEX=False`）。
- **根因**：.pyd 在 `agent/` 子目录，而 `agent/` 不在 `sys.path`，直接 `import fast_index` 找不到。
- **解决**（已修复）：改用包内导入 `from agent import fast_index`。且 tools.py 有 `try/except` 回退——加载失败自动退回纯 Python，项目照样能跑。
- **面试延伸**：这里体现了「优雅降级」——C++ 模块是可选加速，不是硬依赖。缺了 .pyd 项目不崩，只是慢一点。这种"渐进增强"的集成方式，生产里很重要。

## 二、核心设计决策（面试官问"为什么这么设计"）

> 每个决策的回答模板：**「因为面临 X 问题，我选了 Y 而不是 Z，代价是…」**——有 trade-off 才有说服力。

| 决策 | 我为什么这么做 | 反面方案及为什么不选 |
|---|---|---|
| 工具拆原子（search / detail / reviews 分开） | 拆细了模型容易选对、出错好定位、好单独评估 | 一个大而全的 `do_everything` 工具，模型容易乱传参、难排查 |
| 状态显式化（`messages` 列表逐轮累加） | 状态是 agent 的全部，必须可见、可测试、可恢复 | 藏在全局变量/循环变量里，无法并发、无法单元测试 |
| 低 `temperature=0.1` | 工具调用要稳定，温度高模型"跑偏"（写错参数、重复调） | 高温度适合创意写作，不适合结构化工具调用 |
| 工具返回精简摘要 | 每个 token 都是钱，用不到的字段不喂给模型 | 返回完整对象，字段冗余 + 烧 token + 模型分心 |
| 双通道评估（LLM-judge + 硬规则） | judge 懂语义但会飘，硬规则确定但语义盲，互补 | 只用 judge：不可复现、成本高；只用规则：漏语义错误 |
| 第一天就做评估 | 没有指标的 agent 只是"看着能跑"，且评估给回归能力 | 等做完再补评估：改坏了都发现不了 |
| 脏数据防御（`.get()`） | 真实数据不规整，工具层是外部数据的信任边界 | 下标直接访问：一条脏数据就崩掉整个 agent |
| C++ 倒排索引加速搜索 | 搜索是工具热路径，Python O(n) 线性扫描大数据量下太慢 | 纯 Python 优化到头还是 O(n)，用 C++ 索引换 O(1)/O(候选) |

## 三、高频面试问答（模拟对话）

**Q1：什么是 function calling？模型真的执行了工具吗？**
A：不执行。function calling 是给模型一份「工具说明书」（name/description/parameters），模型输出一个"我想调用 X 工具、参数是 Y"的**结构化请求**，我的代码收到后真正执行函数，把结果作为 `role="tool"` 消息回传，模型再基于结果生成文字。模型从头到尾只负责"决定做什么"，执行永远在我的代码里——这是理解 agent 可控性和安全性的基础。

**Q2：你这个 agent 和普通聊天机器人区别在哪？**
A：核心是「循环」。聊天机器人是一次调用，我的 agent 是 Planner-Executor 循环：模型看上下文 → 决定下一步（调工具 or 给结论）→ 我执行工具回传结果 → 再决策，直到模型自己说结束。多步、有状态、能操作外部世界。

**Q3：怎么防止 agent 编造商品或价格（幻觉）？**
A：三层。① 提示词约束：必须来自工具数据、查不到就明说；② 硬校验：预算合规检查抓确定性错误；③ 事实核查：推荐必须能追溯到工具返回的真实数据。关键是——**软约束（prompt）不够，必须有硬校验兜底**。

**Q4：工具怎么设计？为什么拆原子？**
A：三个原则：原子（一个工具干一件事）、可组合（小工具拼出复杂流程）、返回精简（省 token）。拆原子是因为模型更容易选对、出错好定位、也更好单独评估。工具集合就是 agent 的能力边界。

**Q5：agent 的状态怎么管理？**
A：全部状态就是一个 `messages` 列表（system + user + 每轮模型输出 + 每轮工具结果），逐轮累加。状态显式化是 agent 框架和"死代码"的分水岭——显式状态才能测试、才能并发、才能恢复。

**Q6：记忆怎么分层？**
A：短期记忆 = 对话上下文（`messages`），会话结束就没了；长期记忆 = 持久化的用户偏好文件。真实系统里长期记忆要用向量库 + 结构化偏好图谱，我这个是 M2 的最简实现，先建立概念。

**Q7：你怎么评估 agent？为什么用两个指标？**
A：两个指标分开——成功率（任务是否被正确**处理**，含"如实说找不到"这种正确失败）和质量分（处理得好不好，三个维度）。混成一个总分，会丢掉"每次都回应但质量差"和"经常拒绝但一旦做就做好"这两种完全不同的 profile。

**Q8：LLM-judge 可信吗？怎么保证？**
A：单独靠 LLM-judge 不可信（会飘、不可复现），所以用双通道：硬规则兜确定性错误（如预算超支），judge 兜语义。更进一步，judge 用低温 + 固定 prompt + JSON 输出保证稳定性。而且**评估本身也要被评估**——我踩过坑：硬规则把"预算重述"误判成超支，所以每条规则都要用真实 case 验证。

**Q9：遇到死循环 / 反复调工具怎么办？**
A：三层防护：`MAX_STEPS` 硬上限、低 temperature、prompt 明确终止条件。本质是 agent 的"可控性"问题——你不能让一个会烧钱的循环无界跑。

**Q10：你是 C++ 背景，这对 agent 岗有什么优势？**
A：agent 的性能关键路径不在 Python 而在底层——工具执行、推理引擎（vLLM/llama.cpp 核心是 C++/CUDA）、约束解码。我做了个实证：用 pybind11 + C++ 给搜索工具写倒排索引，10 万条商品下查询加速 19–42 倍，而纯 Python 只能 O(n) 线性扫。这就是我区别于纯 Python 候选人的地方——我能把手伸到性能关键路径上。

## 四、电梯陈述（30 秒介绍这个项目）

> 面试开场"介绍一下你的项目"时，照着这个节奏说：

"我做了个电商导购 agent，目标方向是 agent 应用/框架。它支持多轮交互对话，能在用户一句话后，自己多步调用搜索、查详情、看评价、读写用户偏好这些工具，最后给出带价格和来源的推荐。

技术上，我重点解决了两类问题：一是**防幻觉**——用提示词约束 + 预算硬校验双通道，让 agent 查不到就明说、不编造；二是**可评估**——我搭了 30 条任务的评估集，用「成功率 + 质量分」两个指标量化，而不是只看 demo。

过程中踩了不少坑，比如评估任务间记忆污染、硬规则正则误报，这些让我意识到**评估本身也需要被评估**。最后我用 C++ 给搜索工具做了倒排索引，10 万条数据下加速 19–42 倍——这是我区别于纯 Python 候选人的地方。"

## 附：把坑讲成故事的口诀

1. **现象**（一句话，具体到报错）
2. **根因**（挖到技术原理，不是"我改了个参数就好了"）
3. **解决**（具体做法）
4. **反思**（这让我意识到什么更大的原则）

四个层次，缺"根因"和"反思"就成了流水账；有了这两层，面试官会觉得你不是在背答案，是真的趟过水。
